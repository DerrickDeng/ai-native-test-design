# Requirement questions

- [ ] Q1 — QAD-106 AC-05 says "A people session cannot replace the QAD-104 ingest token", and QAD-104 AC-05 says "API pushes require a bearer ingest token; a browser session alone is not enough". Two Stories define the same rule. QAD-104 is the owner and its scenario 07 already covers it. This Story does not retest it. Please confirm that QAD-104 alone owns it. This does not block any scenario.
- [ ] Q2 — QAD-106 AC-03 only says the Dashboard API, run details, and /reports/... "all require a valid session". It does not say how they respond without a session (status code, redirect, or message), nor what /health returns on success. Scenario 05 only asserts that access is refused and no test information is returned, and scenario 06 only asserts that access succeeds without sign-in. The assertions can be strengthened once the responses are confirmed. This does not block the current scenarios.
- [ ] Q3 — QAD-106 AC-04 says "When a later request from a signed-in page receives 401, it returns to the sign-in page", but does not say what the person does on the page to trigger the next request. Scenario 07 says "triggers the next data request" and leaves the exact action to the tester. This does not block scenario 07.
- [ ] Q4 — QAD-106 AC-02 says the rate-limit lockout message is a separate branch, but does not say what triggers it (number of failures, time window) or what the message says. This design writes no scenario for it, and does not assert it with the AC-02 text. This does not block any current scenario.
- [ ] Q5 — The QAD-106 user story says "and be able to end my session", but AC-03 only says "Clicking Sign out returns to the sign-in page". It does not say whether the old session becomes invalid right after signing out (for example when going back or opening run details again). Scenario 04 only asserts the return to the sign-in page. Please confirm what happens to the old session after sign-out. This does not block scenario 04.
